확인일: 2026-11-22, America/Los_Angeles. 대상은 `mgr.eminenthospice.com`의 Eminent Hospice Care Office Flow입니다. 현재 판정은 **실환자 처리 승인 대기**이며 `PHI_PROCESSING_APPROVED=false`를 유지합니다.

## Cloudflare 적용 범위 확인

[Cloudflare 최신 HIPAA FAQ](https://www.cloudflare.com/trust-hub/compliance-resources/hipaa/)는 Workers, D1, Access를 HIPAA Attestation of Compliance(AoC) 범위에 나열합니다. 같은 안내는 Enterprise 고객의 BAA 체결과 PHI 처리 전 양측 서명을 요구합니다. 제품이 AoC 목록에 있다는 사실과 이 기관의 BAA가 체결되었다는 사실은 별개입니다. 감사 문서는 별도의 기밀유지 조건 아래 열람합니다.

이번 계정 점검에서 Workers Free, Teams Free Base, eminenthospice.com Free Plan을 확인했습니다. 체결된 BAA는 확인되지 않았습니다. Gmail의 Cloudflare BAA/Enterprise 계약 관련 검색에서도 일치 메일이 없었지만, 이것만으로 다른 경로의 계약 존재 여부를 단정하지 않습니다. Workers Paid나 Zero Trust 유료 플랜을 구매하는 것만으로 BAA가 체결된다고 판단하지 않습니다.

Cloudflare 계정 소유자는 `eminenthospice@gmail.com`, 앱 관리자는 `slee1005@gmail.com`입니다. 문의는 계정 소유자의 Gmail에 발송 전 초안으로 준비했습니다. 구매·업그레이드·BAA 서명은 하지 않았습니다. 가격과 적용 조건은 Cloudflare의 서면 제안이 필요합니다.

## 저장 정보와 표시명

기관 요구사항은 회사 내부 환자번호와 첫 이니셜·성(예: `J. Smith`)입니다. 전체 이름을 입력받아 숨기는 방식 대신, 제한된 표시명 자체를 입력하고 저장하도록 합니다. 운영 모드의 서버 API는 전체 이름 형식의 환자 생성을 거부합니다. 화면의 기본 이름 숨김, 별도 열람 기록, 이름 없는 CSV도 유지합니다. 기존 레코드를 임의로 변환하거나 삭제하지 않습니다.

이 표기를 비식별 정보로 취급하지 않습니다. [HHS 비식별화 지침](https://www.hhs.gov/hipaa/for-professionals/special-topics/de-identification/index.html)은 이니셜과 의료기록번호 등 식별자에 대한 조건을 설명합니다. 현재 앱에는 연결된 입원·기간·기한·청구 상태도 있어, 이름 표시만 줄이는 조치로 비식별화를 주장하지 않습니다. 생년월일·주소·주민번호·보험 식별번호·상세 차트 입력 기능은 추가하지 않습니다. 자유 텍스트에 식별정보를 넣지 않는 직원 교육과 검토가 별도로 필요합니다.

## 확인한 기술 통제

- Access 개별 이메일 허용 목록, 서버 JWT 서명·발급자·AUD·만료 검증, 앱 승인 대기·직원별 역할·TOTP.
- 업무 세션 유휴 15분·최대 8시간, 민감 작업 최근 5분 이내 MFA, 역할 변경 시 세션 해제.
- 업무 레코드와 TOTP 비밀 값의 AES-256-GCM 암호화, 서버 Secret 사용. 기존 키는 교체하지 않았습니다.
- D1 앱 테이블 11개, 감사 UPDATE/DELETE 금지 트리거 2개. 동시 저장·중복 요청·역할 검증에 대한 자동 테스트.
- 실제 관리자 로그인·MFA와 서버 DB 연결 확인. 비로그인·위조 헤더 접근 차단, workers.dev·preview 비활성화.
- Worker 요청 로그 기본 비활성화, API no-store, 브라우저에 환자 데이터 영구 저장하지 않음.

이는 위 통제의 동작 확인이며, 기관 전체의 HIPAA 준수 인증이나 운영 승인서는 아닙니다.

## 백업과 키 복구의 구분

[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)은 Workers Free에서 7일, Paid에서 30일의 시점 복구를 안내합니다. 이 기간은 장기 보존 정책을 대신하지 않습니다. 원격 DB에서 현재 bookmark가 제공되는 것만 확인했고 운영 DB 복구는 수행하지 않았습니다.

현재 `DATA_ENCRYPTION_KEY`는 Worker Secret에만 등록되어 있습니다. 별도 복구 가능한 키 보관과 회전 절차가 완료되어야 합니다. **DB 백업만 있어도 키를 잃으면 레코드와 MFA 비밀 값을 복호화할 수 없습니다.** 기존 키를 새 임의 값으로 덮어쓰거나 삭제하지 마세요. 키를 환경 변수·소스·채팅·로그로 내보내지 않습니다. 향후 승인된 보관처와 방식이 정해지면 기존 키를 보존하는 복구 절차를 먼저 설계합니다.

별도 시험 DB에서 가상 데이터로 내보내기·복원·복호화·감사 검증을 수행하고, 운영 DB를 시험 목적으로 덮어쓰지 않습니다. 장기 백업이 필요하면 계약 범위에 포함된 저장소와 보존·삭제·접근 정책을 먼저 확정합니다.

## 가동 순서

1. BAA, 서비스 적용 범위·설정 조건, 감사 문서 검토와 기관의 운영 증거를 완료합니다. 비공개 계약·감사 원문은 기관 승인 보관처에 둡니다.
2. 가상 데이터로 분리된 시험 환경에서 저장·권한·내보내기·세션 해제·백업·키 복구·부하 및 업무 수용 시험을 마칩니다.
3. 기관 책임자가 증거와 가동 버전을 승인한 후에만 운영 `PHI_PROCESSING_APPROVED`를 변경하고 배포합니다. 현재 값은 변경하지 않았습니다.
4. 제한된 표시명·내부번호만 입력되는지, 기존 MFA와 직원 권한·감사 기록이 유지되는지 확인합니다. 실제 환자 정보를 테스트나 오류 보고·GitHub에 복사하지 않습니다.
5. 이상 시 신규 입력을 중단하고 기관 사고 대응 절차를 따릅니다. 플래그를 false로 바꾸어도 기존 PHI 조회·저장이 모두 중단되는 것은 아닙니다. 필요하면 Access에서 접근 차단과 세션 해제를 별도 수행하며, 계약과 데이터 보존 의무는 계속 유지합니다. Access 앱 삭제를 접근 차단 수단으로 사용하지 않습니다.

원본 EHR, 임상 판단, 법정 서명·청구 전송 절차는 이 관리 앱으로 대체하지 않습니다.
